## 2026-08-17: Phase 3 - Identity

`Provider` interface (`ValidateToken`/`CreateIdentity`/`DisableIdentity`/`GetIdentity`) with a real Keycloak-backed implementation - JWKS-verified JWT validation, plus all three admin operations against Keycloak's real Admin REST API (not stubs). Platform-side `identities` linkage table records `(provider, providerSubject)` -> status/`last_login_at`, atomically upserted on every authenticated request so "validate" and "remember this login" can't happen separately.

Since the Keycloak container had no working realm before this (`JWT_ISSUER` pointed at `realms/core`, which didn't exist - only the default `master` realm did), added `infra/keycloak/realm-core.json`, imported via `--import-realm` on every `make local-up` (Keycloak's dev storage has no persistent volume, so this isn't a one-time migration - it's expected to run every restart). Hit and fixed a real Keycloak 26 gotcha along the way: `VERIFY_PROFILE` is enabled at the realm level by default and blocks the password grant with an opaque "Account is not fully set up" error even when the user's own `requiredActions` list is empty; had to explicitly disable it in the realm import.

Validated fully live, not just against the in-memory fake: minted a real token from Keycloak's token endpoint, confirmed `GET /v1/identity/me` returns 401 with no token / a garbage token and 200 with the real one, confirmed the `identities` row lands in Postgres with the correct `provider_subject`, confirmed a second call reuses the same row rather than duplicating it, and separately exercised `CreateIdentity`/`GetIdentity`/`DisableIdentity` end-to-end against the real Keycloak Admin API (create a user, fetch it, disable it, confirm `enabled: false` on re-fetch) via a throwaway verification program (not committed - Admin-API-backed methods aren't wired to an HTTP route yet, so there's nothing in the default test suite that would exercise them against a live Keycloak).

`users.identity_subject` (from the original `0001_core.sql` scaffold) is superseded by the new `identities` table but intentionally left alone - dropping/renaming it is a non-additive schema change with no current reader depending on the new table yet, per this repo's "prefer additive changes" migration rule.

## 2026-08-17: Phase 4 - Users

The platform person/account, separate from Identity: `GET/PATCH /v1/users/me`, `GET /v1/users/{id}`. Ties Phases 3 and 4 together via `Service.EnsureForIdentity` - resolves the User already linked to an authenticated Identity, or provisions and links one on first login, with the display name derived from the token's `preferred_username`/`email` claims. Full soft-delete lifecycle: `active` <-> `deactivated` via the normal `PATCH`, `deleted` only reachable through a dedicated `Service.Delete` (rejected with 400 if attempted via `PATCH .../status`) so it's never accidental and always emits its own `user.deleted` event rather than a generic `user.updated`.

`users` and `identity` stay decoupled in both directions: `users` never imports `identity` (`EnsureForIdentity` takes primitive values and a small `IdentityLinker` interface it defines itself, satisfied structurally); the composition - reading identity's context, deriving a display name, calling `EnsureForIdentity` - lives in `internal/api/session.go`, not in either domain package.

`0004_users_registry.sql` adds `avatar_ref` and relaxes `identity_subject` to nullable (superseded by `identities.user_id`, which supports multiple linked identities per user where the old column only supported one - left in place rather than dropped, per this repo's additive-migration preference).

Validated live end-to-end against real Postgres + Keycloak: no token -> 401 on both `/me` endpoints, first authenticated request provisions and links a User (confirmed via `SELECT` on `identities.user_id`), a second request resolves the same User, `PATCH` updates fields and toggles `active`/`deactivated`, attempting `status: deleted` via `PATCH` is correctly rejected, and all four event types (`user.created`, `user.updated`, `user.deactivated`, `user.deleted`) confirmed landing in `outbox_events`. `Service.Delete` isn't behind an HTTP route yet (no endpoint for it in this phase's scope), so it was verified separately via a throwaway (not committed) program against real Postgres, the same way Phase 3's Keycloak Admin API methods were.

## 2026-08-17: Phase 5 - Devices/Sessions

Per-user device tracking: `POST/GET /v1/users/me/devices`, `DELETE /v1/users/me/devices/{id}`, all scoped to the caller's own user (enforced at the repository query level, not just routing). `Register` upserts by `(userID, clientDeviceID)` - first sight creates, repeat sight refreshes profile fields and `LastActiveAt`, and re-registering a previously revoked device reactivates it. `DELETE` soft-revokes (`session_status = 'revoked'`) rather than hard-deleting, so a device disappears from the active list while the row is retained.

No separate `Session` table: `Device.SessionStatus` (`active`/`revoked`) stands in for it, since nothing in this phase needs more than one live session per device - documented as the deferred extension in `backend/core-api/internal/devices/README.md`, same pattern as this repo's other intentionally-scoped-down phases. No events emitted either, matching the roadmap (Phase 5, unlike Phases 2/4, specifies none).

`0005_devices_sessions.sql` adds `client_device_id`, `os_version`, `locale`, `timezone`, `session_status` and the `(user_id, client_device_id)` uniqueness the upsert depends on - safe as a plain (non-partial) unique index since the `devices` table had zero rows before this phase.

Validated live end-to-end against real Postgres + Keycloak: 401 with no token, registered two devices, listed both, revoked one (204) and confirmed it disappeared from the list while a second revoke attempt correctly 404s, re-registered the revoked device and confirmed it reactivated under the *same* device ID with its previous push token preserved (via `COALESCE` in the upsert - re-registering without repeating `pushToken` doesn't wipe it), and confirmed the response body never contains the raw push token string at any point.

## 2026-08-17: Phase 6 - Authorization / Access

The last of the six foundation phases. `authz.Service.Can(subject, action, resource)` - the literal signature the roadmap asked for - is now the one entry point every domain module uses instead of implementing permission logic independently. Two layers, as specified: RBAC roles (`platform.admin`, `support`, `moderator`) in Postgres, and a real OpenFGA-backed fine-grained `Provider` for `Can`/`Grant`/`Revoke`. `AssignRole(platform.admin)` writes to both - the role in Postgres and the equivalent `admin` relation on a singleton `platform:core` object in OpenFGA - so `Can`/`IsPlatformAdmin` see it without a caller needing to know both systems exist.

First concrete consumer: `GET /v1/users/{id}`, previously authenticated-only (documented as a known gap in the Phase 4 entry above), now enforces "self or `platform.admin`" through `authz`, via a `users.AccessChecker` interface `users` defines but doesn't implement (composed in `internal/api/authz_adapter.go`, keeping `users` decoupled from `authz` the same way it's decoupled from `identity`).

Two real bugs found and fixed via live testing against the actual OpenFGA server (not assumed from the SDK docs):
- The `CanViewProfile` policy originally had a speculative fallback `Can()` call against an undefined `user_profile`/`view` relation, intended as "where Phase 8 plugs in" - but `Check()`-ing a type/relation that doesn't exist in the model is a genuine OpenFGA error, not a graceful `false`, and broke every cross-user request with a 500. Removed; Phase 8 will add the model and the check together once there's real relationship data.
- `AssignRole`/`RevokeRole` are documented (and relied on) as idempotent, but the OpenFGA server version this repo runs locally (`openfga/openfga:v1.9.5`) doesn't honor the Go SDK's built-in `Conflict.OnDuplicateWrites`/`OnMissingDeletes` write options despite the SDK sending them - confirmed directly via `curl` against the write API, not assumed. `openfga.Provider.Grant`/`Revoke` now detect the resulting `write_failed_due_to_invalid_input` error via the SDK's typed `FgaApiValidationError` and treat it as success, since in context (Grant only ever writes, Revoke only ever deletes) it always means "this was already a no-op."

OpenFGA's `memory` datastore is exactly as ephemeral as Keycloak's dev-mode storage (confirmed: `{"stores":[]}` after every container restart) - `openfga.Provider`'s constructor finds-or-creates its store and authorization model by name at startup, self-healing the same way the Keycloak realm import does.

Validated live end-to-end against real Postgres + Keycloak + OpenFGA: two distinct Keycloak users, self-view via `/v1/users/{id}` (200), cross-user view without a role (403, `ACCESS_DENIED` envelope), granted `platform.admin` and confirmed cross-user view now succeeds (200) - cross-checked at every layer: the HTTP response, the `user_roles` Postgres row, and the actual OpenFGA tuple via `POST /stores/{id}/read`. Also separately verified the idempotent grant/revoke/revoke-again cycle from both starting states (already-granted and not-yet-granted) via a throwaway (not committed) program, the same pattern used for Phase 3/4's admin-API/delete verification.

## 2026-08-17: Phase 7 - Tenants / Organizations

The reusable multi-tenancy boundary: `Tenant` + `Membership` (`owner`/`admin`/`member`), scoped to an Application (Phase 2). This phase had the least concrete guidance of any so far - no example endpoints anywhere in the roadmap, unlike every prior phase - so both the endpoint set (`POST/GET /v1/tenants`, `GET/PATCH /v1/tenants/{id}`, `GET/POST /v1/tenants/{id}/members`, `DELETE .../members/{userId}`) and the decision to treat "Tenant" and "Organization" as one resource (rather than two structurally-redundant tables, given the roadmap gives Organization no distinct fields) are this pass's own scoping, documented as such in `backend/core-api/internal/tenants/README.md`.

Deliberately does *not* route tenant-role checks ("is this user an owner/admin of this tenant") through `authz.Service`/OpenFGA, even though Phase 6 just built that - answered directly from `Membership` data instead, since it's this package's own data, not the kind of cross-domain relationship question `authz` exists for. Using the generic ReBAC layer for a plain membership lookup would have been reaching for infrastructure the requirement didn't call for.

Validated live end-to-end against real Postgres + Keycloak with two distinct users and a real Application: create (owner auto-membership), non-member GET (403), non-member trying to add themselves as a member (403, can't self-escalate), owner adding the second user as a plain member (201), that member's GET now succeeding (200), that member's PATCH attempt on the tenant correctly denied (403, `owner or admin role required`), `GET /v1/tenants` correctly scoped to only the caller's own tenants, and self-removal ("leave") succeeding and immediately revoking access - cross-checked against the actual `tenant_memberships` row count in Postgres, not just the HTTP response.

## 2026-08-17: Phase 8 - Relationships / Social Graph

A generic relationship graph: `request`/`accept`/`decline`/`remove`/`block`, exactly the five actions the roadmap named, built on the `relationships` table that already existed in the original scaffold (`app_id`, `user_a`/`user_b`, `relationship_type`, `status`, `metadata`) - this package treats `user_a`/`user_b` as requester/target by its own convention rather than renaming the columns, since the table's `LEAST`/`GREATEST` uniqueness constraint doesn't care which side holds which. `RelationshipType` stays product-defined throughout (a plain string never validated against a fixed platform enum), matching the roadmap's explicit "do not encode partner/friend/follower as fixed platform behaviour."

Three genuine bugs found and fixed via live testing:
- `writeDomainError`'s `default` case in `devices`, `tenants`, and `relationships` (everything built since Phase 2's `applications`) was silently swallowing unexpected errors as a bare 500 with no server-side log line - `applications` had the fix, the other three didn't. All three now log via `slog` with the correlation ID, matching `applications`.
- `jsonb` `metadata` scanning into `map[string]any` was unverified until tested live - confirmed working via pgx v5's built-in codec, no manual `json.Unmarshal` needed.
- Originally, `Request` returned a conflict for *any* existing row regardless of status, including `ended` - meaning once two users' relationship ended, that pair could never request again, for that type, ever. Real products need "unfriend, then re-friend later" to work; fixed by adding `Repository.Revive`, which resets an ended row back to `pending` under the new requester/target instead of insisting on a fresh row. Verified live: the exact same relationship ID flipped from `ended` back to `pending` with the requester/target correctly swapped.

Validated live end-to-end against real Postgres + Keycloak with three distinct users and a real Application: request with `jsonb` metadata, requester attempting to accept their own request (403), target accepting (200, active), accepting again (409, already active), get/list scoped to participants, remove/unfriend by either participant (204, confirmed `ended` in Postgres), blocking a stranger with no prior relationship (creates a row directly in `blocked`), the revive path (re-requesting after `ended` reuses the same row), and `relationship.created` landing in `outbox_events` for both a normal request and a direct-to-`blocked` row.

## 2026-08-17: Phase 9 - Groups / Circles

A generic grouping primitive: `Group` + `GroupMember`, deliberately not hardcoded to one use case (friend circles, families, teams, communities, workspaces, gaming guilds are all the same shape). Unlike Phase 7's `Tenant` (a fixed owner/admin/member hierarchy, justified there since tenancy is an infrastructure/access-control concept), `GroupMember.Role` here is a free-form, product-defined label never validated against an enum or used for authorization - the platform enforces exactly one structural bit, `IsManager`, orthogonal to whatever the product calls that member's role. Any manager can promote/demote any other member's `IsManager` bit, including their own or the creator's - no "owner outranks admin" hierarchy is invented, since the roadmap never asked for one; a product that wants that layers it on top of this primitive.

Validated live end-to-end against real Postgres + Keycloak with two users and a real Application: created a group with the creator auto-granted manager status, non-member GET denied (403), added a second user with the free-form role label `"child"` (confirmed stored and returned verbatim, not coerced into any fixed set), that plain member's attempt to update the group and to self-promote both correctly denied (403), the creator promoting them to manager with a different free-form label (`"parent"`), confirmed the newly-promoted manager could then update the group themselves, and self-removal ("leave") succeeding and confirmed against the actual `group_members` row count in Postgres.

## 2026-08-17: Phase 10 - Realtime Platform

A new service, `backend/realtime-gateway`, rather than a module bolted onto `core-api`: WebSocket connections are long-lived and stateful in a way REST handlers aren't, the Helm chart already declares `realtime.replicas: 2`, and this service only ever reads Postgres (resolving an authenticated identity to a platform user ID), never writes to it. The WebSocket handshake and frame protocol are hand-rolled (`internal/ws`, RFC6455: SHA1+base64 `Sec-WebSocket-Accept`, manual masked frame read/write) rather than pulling in a third-party WS library, matching this repo's existing preference for owning small protocol surfaces outright.

Cross-replica correctness is the core design constraint: a naive process-local connection registry would only deliver messages to subscribers on the *same* replica a publish happened to land on. `internal/hub` fixes this by fanning every channel/user/device publish out over Redis pub/sub (`PSubscribe` on `rt:channel:*`, `rt:user:*`, `rt:device:*`), so delivery is correct regardless of which of the two replicas a given subscriber's connection is on. `internal/presence` tracks per-device online status the same way, in Redis with a TTL rather than Postgres, so an unclean disconnect (crash, network partition) simply ages out instead of needing an explicit cleanup path or leaving stale "online" state around.

New shared package: `packages/go/platformkit/jwtverify`, a narrow JWT/JWKS verifier (`golang-jwt/v5` + `keyfunc/v3`, already dependencies via `core-api`'s identity module) - this service needs to verify bearer tokens but never mint them or call Keycloak's admin API, so it gets a smaller dependency than `core-api/internal/identity`'s full `Provider`.

One real concurrency bug avoided during design, not caught after the fact: initially considered having the read loop write pong replies directly to the socket while a separate write loop also wrote to it - recognized as unsafe (`net.Conn` guarantees one concurrent reader and one concurrent writer, not two writers) before any code was written, and redesigned so a `pong` channel feeds the same single `writeLoop` that already owns all other writes.

One real bug found via live testing, not a unit test: `hub.Register` evicts a same-replica reconnect by closing the old connection's `Send` channel, but the old `writeLoop` was simply returning on that signal without closing the underlying socket - leaving the evicted connection's `readLoop` blocked for up to the 70s read timeout, holding a goroutine and file descriptor open and never sending the client a close frame. Caught by a live test that reconnected the same `(userID, deviceID)` and expected the old connection to see a close promptly; it didn't. Fixed by having `writeLoop` close the socket itself when it detects `Send` was closed for eviction (as opposed to normal shutdown via `done`), which unblocks `readLoop`'s `Read` immediately.

Unit tests: `internal/presence` (5 tests) and `internal/hub` (6 tests) run against `miniredis` (a real Redis-protocol implementation in-process, not a mock) - including TTL expiry and heartbeat-refresh scenarios driven via `miniredis.FastForward` rather than real sleeps. No unit tests for `internal/ws` (the handshake/framing/handler glue) - it's thin enough that the live end-to-end pass below is the meaningful test.

Validated live end-to-end against real Valkey + real Keycloak-issued tokens (two distinct users, one with two devices) over a real WebSocket handshake (a from-scratch Python RFC6455 client, no library): connecting without `access_token` and with a garbage token both correctly rejected with `401` before the upgrade; a valid connection receives `connected` with the resolved platform user ID; subscribe/publish/broadcast delivers to every other subscriber of a channel (and to the publisher itself, confirming there's no accidental self-exclusion); publishing to a channel without subscribing first is rejected; a direct message reaches every device the target user is connected on (confirmed against a user with two live connections) and does not leak to the sender's own other device; reconnecting the same `(userID, deviceID)` evicts the prior connection, which - after the fix above - now sees its socket closed promptly instead of lingering; and presence was confirmed directly in Valkey (`presence:<userID>:<deviceID>` appears with a live TTL while connected via `valkey-cli`, and disappears immediately on a clean disconnect).

## 2026-08-18: Phase 11 - Messaging

`Conversation`/`ConversationMember`/`Message`/`Delivery`/`ReadState`/`Reaction`/`Attachment`, built on the pre-existing `conversations`/`conversation_members`/`messages` tables from the original scaffold (same "adapt to what's already there" pattern as Phase 8's `relationships`) plus new tables for attachments, deliveries, read state and reactions. `ConversationType` (`direct`/`group`/`custom`) is a closed enum, matching the roadmap's own fixed list; `Message.Type` is a free-form, product-defined string (TEXT/IMAGE/FILE/SYSTEM/CUSTOM are the roadmap's own examples of what future products can extend), the same "do not hardcode product concepts" convention already applied to `RelationshipType` and `GroupMember.Role`.

The core design problem this phase actually solved: realtime delivery through the Realtime Gateway (Phase 10) and durable storage are two different services with two different Postgres/Redis relationships, and the roadmap explicitly asks for them to stay separate ("Implement realtime message delivery through Realtime Gateway. Implement durable storage separately."). Solved by extracting the Redis pub/sub wire envelope that was previously private to `realtime-gateway/internal/hub` into a new shared package, `packages/go/platformkit/rtbus` - both `hub` (consuming) and `messaging` (producing, this phase) now depend on the identical `Message`/`Kind`/channel-prefix contract instead of `messaging` hand-rolling a JSON shape that happens to match today and drifts tomorrow. `core-api` gained its first real Redis client wiring in the process (previously only TCP-health-checked, per the standing "deferred to whichever domain module first needs it" note) - `messaging.Service` depends on it through a narrow `Realtime` interface (`ToUser(ctx, userID, payload) error`), the same consumer-defined-interface pattern as `users.AccessChecker`, satisfied directly by `rtbus.Publisher` in production and a fake in unit tests.

Two scoping decisions, both documented in `backend/core-api/internal/messaging/README.md`: direct-conversation dedup (requesting a new `direct` conversation between a pair that already has one returns the existing thread) is enforced at the application layer, not a DB constraint, since the member pair lives in a separate table from `conversations` - a documented, accepted race on truly concurrent creates. And conversation membership removal only supports self-removal ("leave"); unlike `groups`, the roadmap defines no role/permission concept for conversations that would justify letting one member remove another.

Validated live end-to-end against real Postgres + Keycloak + Valkey + a real realtime-gateway process, using two distinct users: created a `direct` conversation, confirmed requesting a second one between the same pair returned the identical conversation ID (dedup), confirmed `direct` conversations reject membership changes (403) while `group` conversations allow adding a member and reject one member removing another who isn't themselves (403) while self-leave succeeds (204). The cross-service seam - the actual point of this phase - was verified with one user connected live over a real WebSocket to realtime-gateway while the other user sent a message purely over core-api's REST API: the connected client received a `message.new` push with the correct conversation ID, sender, and body, with zero WebSocket-side action (no subscribe) required - confirming core-api's Redis publish and realtime-gateway's hub subscribe agree on the wire format end-to-end, not just in unit tests against the same in-process struct. Also verified live: delivery acknowledgement (idempotent - acking twice keeps the first timestamp), read-state set/get, reactions (idempotent add/remove, confirmed via the same reaction ID returned on a duplicate add), an attachment round-tripping through a message, cursor-based message pagination across multiple pages with no duplicates or gaps, and the `message.sent` outbox event row confirmed directly in Postgres. No errors in either service's logs across the entire validation pass.

## 2026-08-18: Phase 12 - Notification Platform

`Notification`/`NotificationTemplate`/`NotificationPreference`/`NotificationDelivery` across all five roadmap-named channels (push/email/sms/in_app/realtime), with quiet hours, category opt-outs, delivery status, and retries. The pre-existing scaffold table `notifications` turned out to already be shaped as a single-channel delivery attempt (`category`, `channel`, `payload`, `status`, `delivered_at`) rather than the logical, potentially multi-channel request a caller sends - same "adapt to what's already there" pattern as `relationships` (Phase 8) and `conversations` (Phase 11). It became `NotificationDelivery`'s table (extended with `notification_request_id`/`provider_ref`/`error`/`attempts`/`updated_at`); the logical request got a new `notification_requests` table.

The real design problem this phase solved, matching the roadmap's own "applications should call the Core Notification Service, not FCM/APNs directly": no real APNs/FCM/SES/SMS account exists for local development, and the roadmap's own Cloud Rule says local dev must stay possible without paying for production infrastructure - unlike Postgres/Redis/Keycloak/OpenFGA, these providers have no honest local-equivalent server. Rather than fake success everywhere, only `push` got a *genuinely* testable integration: `senders.PushSender` checks whether the recipient has an actual registered device with a push token (reusing Phase 5's `devices` domain through a narrow `DeviceLookup` interface) before "sending" - a user with zero devices gets a real failure, not a simulated one. `email`/`sms` use `senders.LogSender`, an honest log-and-succeed local stand-in structured so a real provider client can implement the same `ChannelSender` interface later. `realtime` and `in_app` needed no external provider at all: `realtime` publishes over the same `platformkit/rtbus` bus `messaging.Service` (Phase 11) already uses, and `in_app`'s "delivery" is trivial by construction - the `Notification` row, already durable before any sender runs, *is* the in-app inbox entry.

Two access-control decisions, both reusing Phase 6's `authz.Service` rather than inventing new permission logic: `Send` is self-or-platform.admin (this platform has no caller identity distinct from "a user" yet, so letting any authenticated caller notify anyone else would allow spam), and template management is platform.admin-only (templates are cross-cutting app configuration, not a per-user action). `AdminChecker` is satisfied directly by `*authz.Service` - identical method signature to `IsPlatformAdmin`, no adapter needed, unlike `DeviceLookup`.

## 2026-08-18: Phase 14 - Search Platform

`SearchDocument`/`SearchProvider` (`packages/go/platformkit/searchidx`, new shared package) behind a platform search API - "applications should not access OpenSearch directly" is the roadmap's own framing, and `core-api/internal/search.Service` is that boundary. `SearchDocument.Type` is a free-form, product-defined string (`"user"`, `"application"`, `"message"`, or anything future - never a fixed platform enum), matching this repo's established convention.

The real work of this phase was making indexing genuinely event-driven, per the roadmap's own example ("`user.updated` → search index worker"): a new `backend/worker/internal/indexer` package polls `outbox_events` for a specific, recognized set of event types (`user.*`, `application.*`, `message.sent`), turns each into a `searchidx.Document`, applies it to OpenSearch, and marks only those rows published - deliberately leaving every other event type's row untouched (`published_at` stays `NULL`) so a future outbox-to-Kafka relay (still a documented gap since Phase 2) can find and process everything, not just what this indexer already claimed. This is `worker`'s first real job; previously it was a heartbeat skeleton.

One real architectural constraint drove the biggest scoping decision: `worker` and `core-api` are separate Go modules, so `worker` cannot import `core-api`'s internal domain packages to re-read a full entity record when an event fires, and there's no service-to-service auth built yet to fetch one over HTTP instead. Indexed documents are therefore thin - only whatever fields the triggering event's *existing* outbox payload already carries (e.g. `message.sent`'s `{id, conversationId, senderId, type}`, not the actual message body text), never a full re-read. Documented explicitly in both `search/README.md` and `worker/README.md` as a deliberate scope-down, not an oversight - the alternative (fat events carrying full entity content, or a new cross-service RPC layer) is real added complexity this phase's scope didn't call for.

Validated live end-to-end against real Postgres, OpenSearch, and a real worker process - and, notably, against **real historical data**, not just fresh test fixtures: every prior phase's live validation (Phases 2, 4, 11) had already been writing `user.*`/`application.*`/`message.sent` events into `outbox_events` that nothing had ever consumed, since no worker existed until now. The moment the worker started polling, its very first pass indexed all of it - confirmed via `GET /v1/search?type=user` and `?type=message` returning real users and messages from earlier sessions, not placeholders. Then verified the event-driven path with a fresh event: updated a user's display name over the real `/v1/users/me` API, confirmed the change was *not* yet searchable immediately after (query returned zero results), waited past the indexer's 2-second poll interval, and confirmed the exact same query now found it - proof the indexing path is actually reactive, not just working at startup. Also verified live: manual admin-only index/delete (403 for a non-admin, 204 and a correctly-appearing/disappearing document for a platform.admin, accounting for OpenSearch's ~1s near-real-time refresh interval), and cross-checked the outbox table directly - every recognized event type across the whole platform's history was `published_at`-marked, while unrecognized types (`file.uploaded`, `notification.*`, `relationship.created`) were confirmed still `NULL`, exactly as designed. No errors in either service's logs across the entire validation pass.

## 2026-08-18: Phase 15 - Background Jobs

`Job`/`JobStatus`/`JobAttempt` with all six roadmap capabilities (immediate/scheduled/delayed/recurring/retry/dead-letter). `core-api/internal/jobs.Service.Enqueue` is the entire HTTP-facing cost - a single insert - never a handler running inline, per the roadmap's own "do not execute heavy jobs inside HTTP request handlers." Execution is `backend/worker/internal/jobrunner`'s job: claim due rows (`SELECT ... FOR UPDATE SKIP LOCKED`, short transaction), then run each handler with **no** transaction open - deliberately different from Phase 14's search indexer, which holds its claiming transaction through a (fast) OpenSearch call. A job's handler is explicitly allowed to be slow (a webhook call), so holding a Postgres row lock for the duration would itself be the "heavy work" the roadmap says to avoid.

Two built-in handlers ship: `Echo` (an honest, always-succeeding smoke-test primitive) and `Webhook` (a genuine `POST` to a caller-supplied URL). Webhook is what makes this phase's retry/backoff/dead-letter behavior something live validation could actually prove: pointing a job at a dead port produces a real `connection refused`, not a simulated failure, so retrying it and watching it eventually dead-letter demonstrates the real mechanism, not a mocked one - the same design principle Phase 12 used for push notifications (check a real precondition - a registered device token - rather than fake success).

One real bug found and fixed during live validation, not caught by unit tests: `Repository.Create`'s INSERT used `NULLIF($1,'')` directly in SQL text for the optional `app_id`/`created_by` `uuid` columns, which fails with `column "app_id" is of type uuid but expression is of type text` - Postgres can't infer the right type for a bare empty-string literal against a `uuid` column from SQL text alone. Fixed by moving the empty-to-nil conversion to Go (a `nullIfEmpty` helper passing a real `nil` parameter, which pgx binds with the correct type via normal parameter binding), the same pattern every other module in this repo already uses for nullable columns - this repository had briefly drifted from it.

Validated live end-to-end against a real Postgres + worker process, using real timing (no mocked clock): enqueued an immediate `echo` job and confirmed it completed within the 1-second poll interval; enqueued a `delayed` job (5s) and confirmed it stayed `scheduled` immediately after creation, then `succeeded` once its delay elapsed; enqueued a `webhook` job against a real local HTTP server and confirmed it actually received the POSTed body; enqueued a `webhook` job against a genuinely dead port (`connection refused`, not simulated) with `maxAttempts: 3` and watched it fail, retry after a ~2s backoff, fail again, retry after a ~4s backoff, fail a third time, and land in `dead_letter` - attempt timestamps matched the exponential backoff curve exactly, and all three `job_attempts` rows recorded the real connection error; enqueued a `recurring` job (3s interval) and confirmed it executed multiple times automatically, resetting its attempt count each cycle; and confirmed cross-user access control (403 for a stranger viewing another user's job, 200 for a platform.admin, `ListMine` correctly scoped to only the caller's own jobs). No errors in either service's logs across the entire validation pass (webhook failure logs from the intentional dead-port test excluded, as expected).

## 2026-08-18: Phase 19 - Audit

A central Audit Service (`core-api/internal/audit`) covering exactly the roadmap's named fields - actor, action, resource, timestamp, correlation ID, application, tenant, device context "when appropriate", metadata - built on the Phase 1 scaffold's `audit_events` table (confirmed empty before this phase), extended rather than replaced with `tenant_id`/`device_id`. "Audit must be immutable from normal application APIs" is the roadmap's own explicit requirement, enforced twice: by omission (`Repository`/`Service`/HTTP all expose only `Record`/`Get`/`List` - there is no `Update` or `Delete` method anywhere in the Go API for a bug or an oversight to accidentally call), and, going further than any prior phase's single-layer enforcement, at the database itself via a `BEFORE UPDATE OR DELETE` trigger that unconditionally raises an exception - confirmed live that a raw `UPDATE`/`DELETE` issued directly over `psql`, bypassing this repo's Go code entirely, is rejected.

Two deliberate scoping decisions, both documented in `audit/README.md`: writes are direct and synchronous, not routed through the transactional outbox Phases 14/18 use, since a security-relevant record needs a stronger guarantee than "eventually, once a worker gets to it"; and only one real producer is wired this phase - `authz.Service.AssignRole`/`RevokeRole` (granting or revoking a role, including `platform.admin`) - the one action in the platform that was already an unambiguous fit, rather than retrofitting every module's every write.

Wiring that one integration surfaced a genuine, new-to-this-session problem: `authz.Service` needs to report role changes to `audit.Service`, but `audit.Service` needs `authz.Service` as its own `AdminChecker` to gate `Get`/`List` - a construction-order cycle where neither package can be built first. Safe because the only method that dereferences the field `SetAuditService` sets is never called during synchronous startup - only later, from an actual `AssignRole`/`RevokeRole` request, by which point the wiring has always already finished. The audit write itself is best-effort on the authz side: a failure to record is logged, not returned, so an audit-service hiccup can never block a legitimate role change.
