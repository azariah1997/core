Product Vision

The purpose statement and positioning, verbatim from the product spec (apps/pulse/docs/PRODUCT_SPEC.md §2, §5).

What Pulse is

Allow people who care about each other to communicate presence, emotion and attention without needing to type or speak. Pulse is not another WhatsApp, Instagram, Snapchat or conventional messaging app — text is not the centre of the product. The product centres around touch, presence, mood, signals, haptics, relationships, shared moments. The primary interaction is physical/emotional, not textual.

Positioning

Not narrowly "I miss you app" — that was only the starting interaction. The broader product: a private non-verbal communication network for the people who matter to you.

"Feel someone thinking about you." · "Say something without saying anything." · "A social network you feel instead of read."

Architectural dependency (never inverted)

Pulse
  ↓
Core Platform

Core must never acquire a Pulse-specific concept. Pulse consumes Core APIs/SDKs/events — it never reimplements identity, relationships, realtime, notifications, or trust & safety.

North-star metric candidate

Weekly Connected Pairs with Reciprocal Interaction — two connected people who both intentionally interacted with each other during the week. More meaningful than raw app opens. The critical product question: does Pulse remain emotionally useful after the novelty disappears?

Product Principles

From product spec §105 — "Product Principles That Must Never Be Lost." Every phase of implementation is checked against these before being called done.

  • Pulse is non-verbal first.
  • Touch is more important than text.
  • Emotion is more important than engagement metrics.
  • The product should feel private.
  • Partner is special, but Pulse is not couples-only.
  • A user can have one Partner and multiple Friends.
  • Today's Mood is passive emotional presence.
  • Pulse is active emotional presence.
  • Live Touch is synchronous presence.
  • Knock is lightweight attention.
  • Custom Signals become a private language.
  • Do not create surveillance.
  • Do not create relationship pressure.
  • Do not create manipulative streaks.
  • Do not become another messaging app.
  • Core Platform owns generic infrastructure. Pulse owns Pulse-specific product behaviour.
  • Every interaction must respect consent, permissions, blocking and privacy.
  • The application must remain usable globally.
  • iOS and Android platform limitations must be handled honestly.
  • Realtime behaviour must degrade gracefully to notifications.
  • Everything important must be observable.
  • Every AI change must remain understandable and reviewable.

No streak pressure (spec §32)

Never: "You lost your 148-day love streak!"

Instead, if statistics are shown at all: "12 little moments together this week." Pulse creates closeness, not obligation.

People & Relationships

Spec §6-11. A person can have 0 or 1 romantic Bond, plus multiple Close Friends, Friends, and custom Circles — Pulse is not exclusively for couples.

Partner Bond 0 or 1

One optional, explicitly mutual romantic connection. Never established automatically. States: PENDING → ACTIVE → ENDED, or BLOCKED.

Unlocks: Live Touch, Long Pulse, private touch language, intimate mood visibility, shared moments, special animations, future wearable interactions.

Friends many

Regular connections. Can participate in less-intimate interactions: Pulse, Knock, Mood, Reactions, Circles. Exact permissions are Pulse product policy.

Close Friends many

A classified subset of Friends who may receive more private moods, additional signal types, closer presence interactions. Not everyone sees everything.

Circles custom

Custom groups (Closest Friends, Family, University, Work, Gaming, ...). Membership is private by default. Primarily controls mood audience and future group interactions.

Relationship terminology

Bond (romantic) · Close Friend · Friend · Circle · Connection (generic term for any of the above)

Sending a Pulse — Live (receiver online, foreground, realtime session available)

1
Sender selects a connected person, presses and holds
2
PulseStart sent to server (not a continuous stream)
3
Server authorizes (connected, not blocked, Bond-gated features checked, rate limit) and relays via hub.PublishToUser

6
Receiver's haptic stops. Server computes/validates the authoritative duration — client-submitted duration is never fully trusted
7

Sending a Pulse — Offline / Background (receiver not available for Live Pulse)

1
Sender completes the Pulse gesture
2
Pulse stored (durable, server-authoritative)
3
Push notification requested through Core notifications.Service.Send — Pulse never calls FCM/APNs directly
4
Receiver gets a platform-appropriate notification/haptic; the app may reproduce/show the Pulse duration when opened

iOS and Android background/haptic restrictions differ — never promise continuous remote vibration while backgrounded/locked if the OS doesn't allow it. See Risks.

1
User selects a visual/symbol (never a free-text status)
2
User picks an audience: Partner only / Close Friends / Selected Circles / All Connections / Custom / Private
3
Mood persists, expires at the user's local day boundary (timezone-correct)
4
Authorized viewers see the Mood; unauthorized viewers see nothing
5
Viewer responds non-verbally — Pulse, Knock, Hug signal, Heart signal — no obligation to explain, no text reply required

Live Touch session

1
One participant invites the other into a Live Touch session (Bond-gated)
2
Receiver accepts; both connect to a shared realtime channel (pulse:live-touch:{sessionId})
3
Either side touches → remote haptic starts on the other device, bidirectionally, with minimal latency
4
Touch release → remote haptic stops
5
Session ends (explicit end or disconnect/timeout) → durable completion recorded, individual touch events are never persisted

Genuine Core gaps found (2)

1. Deep linking (§52). No deep-link infrastructure exists anywhere in Core. Recommendation: build in Pulse (mobile-app-level Universal Links/App Links config + a thin POST /v1/pulse/invites endpoint), not Core — this isn't a generic-enough capability to justify a Core change yet.

2. Multi-device delivery policy (§73-74). Core's notifications sends to all of a user's active devices; nothing expresses "primary device only" / "wearable preferred" as a caller policy. Recommendation: defer — Phases 4-5 work correctly against "all active devices," revisit once wearables (Phase 17) are real.

5Push Fallback Done

Receiver offline → real presence check → Core Notification → push, live-validated end to end - including both an honest real failure (no registered device) and a genuine real success (after registering one). Required two real, carefully-scoped Core changes, both decided with explicit user sign-off since they touch shared platform capabilities: realtime-gateway gained GET /v1/presence/{userId} (exposing its already-existing presence tracker), and notifications.Send was relaxed from self-or-admin to any authenticated caller, attributed via a new SentByUserID field. 6 new backend tests for the delivery-mode decision alone (live/push/presence-failure/notification-failure), on top of Phase 4's suite.

7Knock Done

POST /v1/pulse/knocks - a short predefined haptic pattern ("quicker, lighter... a nudge, not a hold", spec §18), not a held gesture, so one API call: Create+Start+Stop back-to-back, same shape as Pulse Back. Reuses Pulse's exact interactions table and state machine via a second Type value rather than a parallel implementation - a new nullable pattern column (one of four predefined names: double_tap, triple_tap, long_short, short_long_short) is the only schema change. This required generalizing Notifier from a Pulse-specific NotifyPulseReceived(receiverUserID, durationMs) method to one shared Notify(receiverUserID, category, title, body, data) method, and deriving Start/Stop's realtime event names and analytics event names from Interaction.Type instead of hardcoding them - the extensible architecture this phase was explicitly asked to leave behind for Phase 11's Custom Signals. Live-validated end to end with real Keycloak users: a real WebSocket connection receiving both knock.started and knock.stopped with zero push notifications sent while live; then, with the receiver genuinely offline, one real knock_received notification landing in Core's database attributed to the real sender and carrying the requested pattern, plus durable knock_started/knock_completed analytics events for both runs. Mobile gained a real "Knock" button on the Home tab and incoming-Knock haptic + banner handling.

  • Second Type value on the shared interactions state machine, not a parallel table
  • One-call Create+Start+Stop, reusing the exact authorization/rate-limit/presence logic Pulse and Pulse Back already established
  • Four predefined patterns, server-validated, defaulting to double_tap
  • Notifier generalized to one method shared by every interaction type, not one per type
  • Realtime event names and analytics event names derived from Type, not hardcoded - the extensibility Phase 11's Custom Signals built on
  • Mobile "Knock" button plus incoming-Knock haptic and banner, wired to the real API

9Close Friends & Circles Done

POST/GET /v1/pulse/circles, GET/POST /v1/pulse/circles/{id}/members, DELETE /v1/pulse/circles/{id}/members/{userId} - Circles (spec §10) as a thin wrapper inside pulse-connections over Core's real groups capability (backend/core-api/internal/groups), never a Pulse-owned Circle table. 10Live Touch Done

POST /v1/pulse/live-touch/sessions, .../accept, .../decline, .../end, GET .../{id} - the flagship synchronous two-way touch feature (spec §21), its own module (internal/livetouch/) rather than a third pulse-interactions Type, since it's gated on the caller's real, current active Bond partner specifically (spec §7) - a genuinely stricter shape than Pulse/Knock's Friend-or-Bond. Session lifecycle (invite/accept/decline/end, with a real server-computed duration) is a durable REST flow; touch events themselves are never persisted and never proxied through pulse-api - once active, both participants subscribe to a per-session realtime-gateway channel (pulse:live-touch:{sessionId}) using the mobile app's already-open WebSocket connection and exchange touch.start/touch.stop directly, the lowest-latency path this platform has. An unaccepted invite (2 min) or an abandoned active session (30 min) both expire lazily on the next read, never a background job - an honest proxy for "disconnect handled," since realtime-gateway's hub doesn't broadcast peer-disconnect events today (a documented platform limitation, not silently worked around). Live-validated end to end with the Phase 9 sample Bond pair (Alice ↔ Bob): Bond-gating correctly rejected an unbonded caller and resolved the real partner; an offline receiver got a real push notification; a real two-connection WebSocket round trip relayed touch.start/touch.stop directly between participants at ~790µs measured relay latency; accept/decline/end all transitioned state correctly including a real 409 on double-accept and 403 for a non-participant; duration was computed server-side, never fabricated; and invite-to-accept latency was recorded as a durable analytics property (spec §104's "latency measured"). Mobile ships a real "Live Touch" button (shown only against the real Bond partner), an incoming-invite banner with Accept/Decline, and a LiveTouchScreen with real local haptic feedback on both sides.

  • Session invite/accept/decline/end, Bond-gated, real server-computed duration

11Custom Touch Language Done

POST/GET /v1/pulse/signals, GET/DELETE .../{id}, POST .../{id}/send - a private touch pattern library (new signals module) plus a fourth pulse-interactions Type (TypeSignal) for actually sending one, the same Create+Start+Stop reuse Knock established in Phase 7. A Signal send gets every real guarantee Pulse/Knock already have (connection check, rate limit, live-vs-push delivery) for free. Segments (tap/hold/pause + durationMs) travel through the existing nullable pattern column as JSON - a Phase-7-era comment on that field explicitly anticipated this reuse, so this phase needed no new migration on interactions at all. Server-enforced bounds (max 20 segments, 20-3000ms each, 10000ms total) close Risk #4 below - enforced at creation time, never merely a client-side UI limit. Only a pattern's real owner may ever resolve or send it (signals.Service.Get's own ownership check is pulse-interactions' entire authorization surface for sending); the receiver is always the signal's own bound target, never a client-supplied value - a private pattern can never be redirected to someone it wasn't created for. Live-validated end to end with the Phase 9/10 sample connections (Alice → Bob): creating a real pattern, a real 403 rejecting a stranger's read, real bounds rejecting an oversized segment count and an out-of-range duration, a real push-fallback notification landing in Core's database, and a real WebSocket round trip confirming the receiver's device gets the actual segments array live for local haptic playback - "the pattern itself is the communication" (spec §20). Mobile ships a real Signals screen per connection: compose with local haptic preview, save, send, delete.

  • Private pattern library bound to one specific connection, never a global reusable pattern
  • Server-enforced bounds at creation time - segment count, per-segment and total duration
  • Sending reuses pulse-interactions' Create+Start+Stop as a fourth Type - no duplicated authorization/rate-limit/delivery logic
  • Ownership-only send authorization; receiver always the signal's own bound target
  • Live delivery carries the real segments array for local haptic playback
  • Mobile: compose (with local preview), save, send, delete, per connection

12Moments Done

POST /v1/pulse/moments/{interactionId}/save, GET /v1/pulse/moments, DELETE .../{id} - a private saved-highlights timeline (new moments module), explicitly not a chat history: it stores only a reference to an already-real interaction (type, duration, pattern, the other participant, timestamps), never a copy of its payload. A Moment is a personal bookmark, not a shared record - the two participants in the same interaction each get their own independent row, matching how "save" buttons work everywhere else, enforced by a real Postgres unique constraint on (saved_by_user_id, interaction_id) that also makes re-saving idempotent. moments.Service.Save consumes pulse-interactions in-process via the same pulsemodules adapter pattern Signals and Mood/Live Touch already established, so it never re-implements the sender/receiver-only participation check pulseinteractions.Service.Get already does - it only adds its own rule that the interaction must be completed. No auto-expiry, unlike Mood's deliberate daily decay - a Moment's whole purpose is durability, so retention just means the explicit Delete. Live-validated end to end with the real Alice/Bob/Carol sample users against real Postgres: saving a real completed Signal, a second participant independently saving the same interaction to their own list with the perspective-correct other-user ID, a real 403 rejecting a non-participant, an idempotent re-save returning the same moment, and a real delete/re-list round trip. Mobile ships a real Moments tab (gentle "N little moments together this week" stat per spec §32, computed client-side - never a punishing streak counter - plus per-row delete) and a "Save this moment ♥" button wired into both the Home tab (after a Pulse or Knock completes) and the Signals screen (after a Signal send).

  • References only - no duplication of interaction content, no chat history
  • Personal bookmark model - each participant saves independently, idempotent per caller via a real DB unique constraint
  • Save reuses pulse-interactions' own participation check - no duplicated authorization
  • Only a completed interaction can be saved
  • Gentle stats, never a streak counter - computed client-side from already-fetched data
  • Mobile: real Moments tab (list + delete) and "Save this moment ♥" on Pulse/Knock/Signal completion

13Quiet Hours / Experience Controls Done

GET/PUT /v1/pulse/preferences, .../quiet-hours, POST/GET/DELETE .../mutes - a new pulse-preferences module owning exactly the two fields genuinely Pulse's: notification detail level (Detailed/Private/Silent) and haptic intensity. Quiet Hours and Mute are deliberately not duplicated as Pulse-owned storage - both are real, already-live Core capabilities (notifications.QuietHours, platform-wide trustsafety.Mute) this module is a thin, Pulse-scoped settings surface over, correcting this module's own original planning stub which had assumed Mute needed its own table. A NotifierDecorator wraps the real Notifier both pulse-interactions and live-touch already use - one decorator type structurally satisfies both modules' identically-shaped Notifier interface (Go's structural typing) - and reads the receiver's own preference directly from Pulse's own database before every push: silent skips the notification entirely (the interaction itself still succeeds and is recorded normally), private still sends one but with generic, redacted content, and detailed (the default, applied automatically to every existing user) passes the real content through exactly as every prior phase already did. Quiet Hours needed no equivalent enforcement wiring - Core's own notifications.Service.Send was already suppressing interruptive channels during a receiver's real quiet-hours window before this phase existed. One gap is named and deliberately deferred, not silently built: delivery-time Mute suppression (Architecture Audit's AUTHORIZATION MODEL item 7) needs Pulse to know whether the receiver mutes the sender, but Core's Mute is deliberately self-scoped (a user can only read their own mute list via their own token) - closing this needs a new, unscoped Core capability, which per this platform's Phase-5 precedent for cross-cutting Core changes requires explicit sign-off, not something added silently. Live-validated end to end with the real Alice/Bob sample users against real Postgres and real Core: preferences persisting and round-tripping; Quiet Hours set through Pulse confirmed to write the exact same row Core's own endpoint reads back; Mute/list/unmute confirmed against Core's real global mute table; and all three notification-detail states verified against a real offline-push Knock - silent left Bob's real Core notification count unchanged, private added one real notification with redacted content, and detailed delivered the real title/body/pattern data with zero regression. Mobile ships a real Experience Controls section on the Profile tab.

  • Notification detail level and haptic intensity are Pulse-owned; Quiet Hours and Mute are thin proxies over real, already-live Core capabilities, never duplicated storage
  • One NotifierDecorator, structurally satisfying both pulse-interactions' and live-touch's Notifier interfaces, reads the receiver's own preference before every push
  • Silent suppresses the notification entirely; Private redacts content; Detailed (default) is a zero-regression passthrough
  • Quiet Hours proxy confirmed to write/read the exact same real Core row
  • Mute/list/unmute confirmed against Core's real global mute table
  • Named, deferred gap: delivery-time Mute suppression needs a new unscoped Core capability, pending explicit sign-off
  • Mobile: Experience Controls on the Profile tab (notification detail, haptic intensity slider wired live into HapticEngine, Quiet Hours, Mute/Unmute)

Risks

Named honestly now, before implementation, so they're designed around rather than discovered late.

1iOS background haptic promises. The single highest product risk named in the spec itself. Any implementation implying continuous remote vibration while backgrounded/locked on iOS misrepresents what the OS allows. Phase 4 built Live Pulse only (receiver online, foreground) as its own distinct code path — Offline/background Pulse is deliberately deferred to Phase 5, never blended in as a "best effort" fallback. Still open: real backgrounded-app behaviour on an actual device, blocked on the toolchain gap below.
2One-active-Bond concurrency. Two simultaneous Bond requests targeting the same user must not both succeed. Needs a real concurrency test (two goroutines racing an accept) against Postgres with a partial unique index (WHERE status = 'ACTIVE') as the actual enforcement mechanism — the same lesson Core's own billing/authz modules already learned about not trusting application-level-only invariants.
3Trusting client-submitted duration. Server timestamps are truth; client startedAt/endedAt are UX-only. A test asserting a forged large durationMs is ignored in favor of server-observed timing should exist before Phase 4 is called done.
4Custom signal pattern abuse. An unbounded segments[] array could construct a very long or rapid vibration pattern. Mitigated in Phase 11: explicit server-side bounds (max 20 segments, 20-3000ms each, 10000ms total) enforced at creation time in signals.CreateInput.Validate, never merely a client-side UI limit - live-confirmed rejecting both an oversized segment count and an out-of-range single-segment duration.
5Deep-link / invite-link growth loop intersects Trust & Safety. An open invite-link flow is a natural spam vector — must reuse trustsafety's rate limiting on invite creation, not just on Pulse/Knock sending.
6Toolchain gap for real device testing. This environment has Flutter but no Android SDK and an incomplete Xcode install. Phase 4 shipped a real HapticEngine (Standard tier, Flutter's cross-platform HapticFeedback - genuinely felt on a real device, not a stub) and validated the full mechanic end to end via Chrome/web-server and a Go-based live-check hitting real infrastructure. Still not possible here: the Advanced tier (custom iOS Core Haptics patterns, spec §59, needs native Swift/Kotlin platform-channel code) and any real on-device backgrounded-app behaviour. Name this gap honestly in every phase's validation rather than simulating it.
