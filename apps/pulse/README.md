# Pulse

A global, non-verbal social communication product built as a **consumer** of the Core Platform, never a modification of it.

> Feel it instead of reading it.

Pulse lets people who care about each other communicate presence, emotion, and attention without typing or speaking - starting with **Pulse** (press-and-hold, felt as haptic on the other end), extending to **Mood**, **Knock**, **Live Touch**, and a private **Custom Touch Language** between two people.

The full product specification lives in [`docs/PRODUCT_SPEC.md`](docs/PRODUCT_SPEC.md) (106 sections - vision, product model, phased roadmap, definitions of done, principles). The architecture audit required before any implementation began lives in [`docs/ARCHITECTURE_AUDIT.md`](docs/ARCHITECTURE_AUDIT.md). The live-tracked roadmap/todo/user-flow dashboard is [`docs/control/pulse.html`](../../docs/control/pulse.html) at the repo root.

## Dependency direction

```text
Pulse
  ↓
Core Platform
```

Never the reverse. Pulse consumes Core's identity, relationships, groups, realtime, notifications, files, jobs, workflows, feature flags, remote config, audit, privacy, trust & safety, billing, analytics, and observability through the real Go/TypeScript/Dart SDKs and REST/event contracts - it does not reimplement any of them, and Core never acquires a Pulse-specific concept.

## Layout (matches Core's own conventions)

```text
apps/pulse/
  mobile/     Flutter app (apps/mobile's sibling) - the only Pulse UI surface for now
  api/        Pulse Product API (new Go service) - owns Pulse-specific data, calls Core via coresdk
  modules/    Pulse domain module boundaries (module.yaml + README.md, mirrors Core's modules/*/module.yaml)
  contracts/  Pulse-owned OpenAPI/AsyncAPI (Pulse's own API/events, distinct from Core's contracts/)
  docs/       Product spec, architecture audit, phase-by-phase validation as it happens
```

## Status

Phases 1-11 complete and live-validated: Product Foundation, Connection Experience, Partner Bond, Basic Pulse, Push Fallback, Pulse Back, Knock, Today's Mood, Close Friends & Circles, Live Touch, and Custom Touch Language. `pulse-interactions` decides Live vs. Push once per interaction, from a real presence check against `realtime-gateway` - Live delivers PulseStart/PulseStop (and now KnockStart/KnockStop) over a real WebSocket connection (via `platformkit/rtbus`); Push requests a real notification through Core's `notifications.Send` once the interaction completes, carrying the real final duration (or, for Knock, its pattern). Duration is always computed server-side from its own timestamps, creation is idempotent for mobile network retries, sends are rate-limited, and every interaction records durable `<type>_started`/`<type>_completed` analytics events. Pulse Back (`POST .../pulse-back`) is one API call reusing Create+Start+Stop directly - the receiver of a completed Pulse gets every real guarantee an ordinary Pulse has (authorization, rate limit, a fresh presence check) with no duplicated logic, and its real (never fabricated) duration plus a `pulse_back` analytics event with genuine response-latency are both live-confirmed. Knock (`POST /v1/pulse/knocks`, Phase 7, spec §18) is a short predefined haptic pattern - also one API call, sharing Pulse's exact table and state machine via a second `Type` rather than a parallel implementation; this required generalizing `pulse-interactions`' `Notifier` interface to one `Notify(category, title, body, data)` method shared by every interaction type instead of accumulating a new method per type, which is exactly the extensibility Phase 11's Custom Signals built on. `apps/pulse/mobile` ships a real `HapticEngine`, a working hold-to-Pulse gesture, and a real "Pulse Back" button on the incoming-Pulse banner - all wired end to end.

Phase 5 required two real, carefully-scoped Core changes, both decided with the user's explicit sign-off since they touch shared platform capabilities rather than Pulse's own code: `realtime-gateway` gained `GET /v1/presence/{userId}` (exposing its already-existing presence tracker), and `notifications.Send` was relaxed from self-or-platform.admin to any authenticated caller, attributed via a new `SentByUserID` field - Pulse's sender-notifies-receiver need turned out to be the first real cross-user notification requirement this platform had ever had.

Live-validated end to end: a real WebSocket round trip for Live delivery; for Push, a real presence check confirming `pulsefriend` was genuinely offline, a real notification landing in Core's database attributed to the real sender, an honest real failure ("recipient has no device with a registered push token"), then a genuine real success once a device/push-token was registered; and for Pulse Back, a full Pulse → Pulse Back round trip confirming the reciprocal direction, the durable `inResponseToId` link, and a real 403 when a non-receiver tries to respond. Knock was live-validated the same way: a real WebSocket connection for `pulsefriend` confirming both `knock.started` and `knock.stopped` with zero push notifications sent while live; then, with `pulsefriend` genuinely offline, one real `knock_received` notification landing in Core's database attributed to the real sender and carrying the requested pattern, plus durable `knock_started`/`knock_completed` analytics events for both runs.

Today's Mood (`PUT`/`DELETE /v1/pulse/mood`, `GET /v1/pulse/mood/me`, `GET /v1/pulse/mood/{userId}`) is the platform's first genuinely new domain module since Phase 4 - a passive, wordless emotional-state layer (spec §22-27) built entirely on capabilities Pulse already has: audience is resolved once, at `Set`, from `bond`'s real active-partner record and `pulse-connections`' real Friend/Close-Friend classification - both reused directly as same-process `*Service` dependencies (`internal/mood/pulsemodules`), never duplicated data. Responding to a Mood needed no new backend surface at all - spec §27 names Pulse and Knock themselves as the response, and both already work against any connected user ID. Live-validated end to end with real Keycloak users against real Postgres: `partner_only` correctly resolved to a real bonded partner (and excluded a plain friend), `close_friends` correctly resolved against real classification data, `custom_users` correctly dropped a non-connection ID while keeping a real one, a real stranger and a real friend outside the chosen audience both got the same 404 as "no Mood exists" (never leaking whether one does), expiry landed exactly on local midnight, and Clear removed the real row.

Close Friends & Circles (`POST/GET /v1/pulse/circles`, `.../members`, Phase 9, spec §10) integrates Core's real `groups` capability as Pulse's Circles - a thin wrapper inside `pulse-connections`, never a Pulse-owned Circle table; Core's own `ListMine` isn't scoped per application, so the real adapter (`internal/pulseconnections/core/groups_adapter.go`) filters to Pulse's own AppID client-side. Adding a Circle member requires the caller and the target to already be a real, active Pulse connection (Friend or Bond) - Pulse's own authorization, layered on top of Core's own manager-based one. This unblocked Mood's sixth and final audience value, `selected_circles` (spec §25), resolved from a real Circle's real membership the same "decided once, at Set" way every other audience value already works. Live-validated end to end with real Keycloak users against real Postgres and Core's real `groups` table: creating a Circle, correct `appId` filtering, a real active connection successfully added as a member, a real 403 rejecting a non-connection, member removal, and a `selected_circles` Mood correctly visible to a real Circle member while a real connection who wasn't in that Circle got the same 404 as everyone else outside the audience. Mobile's People tab is now real: create Circles, expand one to see/add/remove members from existing connections, and pick a Circle as a Mood's audience.

Live Touch (`POST /v1/pulse/live-touch/sessions`, `.../accept`, `.../decline`, `.../end`, Phase 10, spec §21) is the platform's flagship synchronous two-way touch feature and its own module (`internal/livetouch/`), not a third `pulse-interactions` `Type` the way Knock was - Live Touch is gated on the caller's real, current active Bond partner specifically (spec §7), a genuinely stricter authorization shape than Pulse/Knock's Friend-or-Bond. Session lifecycle (invite/accept/decline/end, with a real server-computed duration) is a durable REST flow; the touch events themselves are never persisted and never proxied through `pulse-api` at all - once a session is active, both participants `subscribe` to a per-session realtime-gateway channel (`pulse:live-touch:{sessionId}`) using the mobile app's already-open WebSocket connection and exchange `touch.start`/`touch.stop` directly, the lowest-latency path this platform has. An unaccepted invite or an abandoned active session both expire lazily on the next read (no background job), an honest proxy for "disconnect handled" - `realtime-gateway`'s hub doesn't broadcast peer-disconnect events today, a documented platform limitation, not something this phase quietly works around. Live-validated end to end with the Phase 9 sample Bond pair (Alice ↔ Bob): Bond-gating correctly rejected an unbonded caller and resolved the real partner; an offline receiver got a real push notification; a real two-connection WebSocket round trip relayed `touch.start`/`touch.stop` directly between participants at ~790µs measured relay latency; accept/decline/end all transitioned state correctly including a real 409 on double-accept and 403 for a non-participant; and duration was computed server-side, never fabricated. Mobile ships a real "Live Touch" button (shown only against the real Bond partner), an incoming-invite banner with Accept/Decline, and a `LiveTouchScreen` with real local haptic feedback on both sides of a touch.

Custom Touch Language (`POST/GET /v1/pulse/signals`, `.../{id}`, `POST /v1/pulse/signals/{id}/send`, Phase 11, spec §19-20) is a private pattern library (new `signals` module) plus a fourth `pulse-interactions` `Type` (`TypeSignal`) for actually sending one - the same Create+Start+Stop reuse Knock established in Phase 7, so a Signal send gets every real guarantee Pulse/Knock already have (connection check, rate limit, live-vs-push delivery) for free. Segments (`{type: tap|hold|pause, durationMs}`) travel through the existing nullable `Pattern` column as JSON - a Phase-7-era comment on that field explicitly anticipated this reuse, so Phase 11 needed no new migration on `interactions` at all. Server-enforced bounds (max 20 segments, 20-3000ms each, 10000ms total) close the real abuse vector the Architecture Audit named for this phase (Risk #4: an unbounded pattern building a very long/rapid vibration) - enforced at creation time, never merely a client-side UI limit. `signals.Service.Get`'s own ownership check (only a pattern's real owner may ever resolve or send it) is pulse-interactions' entire authorization surface for sending - the receiver is always the signal's own bound target, never a client-supplied value, so a private pattern can never be redirected to someone it wasn't created for. Live-validated end to end with the Phase 9/10 sample connections (Alice → Bob): creating a real pattern, a real 403 rejecting a stranger's read, real bounds rejecting an oversized segment count and an out-of-range duration, a real push-fallback notification landing in Core's database, and a real WebSocket round trip confirming the receiver's device gets the actual segments array live for local haptic playback - "the pattern itself is the communication." Mobile ships a real Signals screen per connection: compose with local haptic preview, save, send, delete.
