# pulse-interactions

The core product mechanic: Pulse (press-and-hold, felt as haptic), Knock, and Custom Signals. Owns the interaction state machine, server-authoritative duration (never trusts client-submitted `durationMs`), idempotent creation, and the Live-vs-Push delivery decision.

**Owns:** `interactions` table (idempotent on `(sender_id, client_request_id)`, server-computed `duration_ms`, `delivery_mode` decided once at Start and never changed).
**Depends on:** Core `relationships` (connection + block check via `ListMine`, no mutation), `platformkit/rtbus` (real-time delivery, fixed service-level dependency), Core `analytics` (durable `pulse_completed` event), Core `notifications` (push fallback), `realtime-gateway`'s presence endpoint (Live-vs-Push decision), `platformkit/ratelimit` (10 sends/min/sender), and, since Phase 11, `signals` - this module's first dependency on a sibling Pulse module (every prior Type only ever needed Core capabilities), reached the same "satisfied directly by a real same-process `*Service`" way `mood` and `live-touch` already reach `bond` (`internal/pulseinteractions/pulsemodules`).
**Realtime (Live path):** delivered via `rtbus.Publisher.ToUser` → `realtime-gateway`'s hub → the receiver's live WebSocket, with `pulse.started`/`pulse.stopped` message types wrapped in the SDK's real `{type, data}` envelope.
**Push (offline path):** `Start` checks the receiver's real presence (`GET /v1/presence/{userId}` on realtime-gateway) exactly once and records the decision as `DeliveryMode`; a receiver offline at that moment gets no live attempt at all, and a single real push notification (Core's `notifications.Send`, `category: pulse_received`) goes out once, at `Stop`, carrying the real final duration.
**Pulse Back (Phase 6, spec §17):** `POST /v1/pulse/interactions/{id}/pulse-back` - one API call, faster than opening a messaging interface. Internally just a normal Create+Start+Stop targeting the original sender, linked via a new `in_response_to_id` column - reused directly rather than duplicated, so a Pulse Back gets every real guarantee an ordinary Pulse does (connection/block check, rate limit, a fresh presence check independent of the original interaction's own delivery mode) for free. Only the real receiver of a *completed* original may respond. Duration is never fabricated - Start and Stop are invoked back-to-back with real timestamps, producing a real (typically single-digit-millisecond) server-measured gap rather than a pretend "quick tap" value. Records a `pulse_back` analytics event with `responseLatencyMs` (spec §80's own named metric: time from the original Pulse being felt to the response).
**Knock (Phase 7, spec §18):** `POST /v1/pulse/knocks` - a short predefined haptic pattern ("quicker, lighter... a nudge, not a hold"), not a held gesture, so it's one API call: Create+Start+Stop back-to-back, same as Pulse Back. Reuses the exact same `interactions` table and state machine as Pulse (a new `pattern` column, nullable, NULL for ordinary Pulses) via a second `Type` value (`TypeKnock`) rather than a parallel table or service. Generalizing this required widening `Notifier` from a Pulse-specific `NotifyPulseReceived(receiverUserID, durationMs)` to a generic `Notify(receiverUserID, category, title, body, data)` - the one method every current and future interaction Type (Knock now; Mood Response, Live Touch, Custom Signals later) shares, instead of accumulating one bespoke method per Type. `Start`/`Stop`'s realtime event names and analytics event names are now derived from `Interaction.Type` (`knock.started`/`knock.stopped`/`knock_started`/`knock_completed` vs. `pulse.*`/`pulse_*`) rather than hardcoded - the "extensible architecture" Phase 7 was explicitly asked to leave behind for Phase 11's Custom Signals. Pattern is one of four predefined names this phase (`double_tap`, `triple_tap`, `long_short`, `short_long_short`, spec §18), validated server-side and defaulting to `double_tap` - not yet the free-form tap/hold/pause segment array Phase 11 will add, but the same nullable string column will hold it without another migration.

**Custom Signals (Phase 11, spec §19-20):** `POST /v1/pulse/signals/{id}/send` - a private touch pattern, felt exactly like a Pulse or Knock, reusing Create+Start+Stop as a third real Type (`TypeSignal`) the same way Knock reused it in Phase 7. `signals` owns the saved-pattern *library* (CRUD, ownership, bounds); this module only ever resolves one by ID (`signalsSvc.Get`, which enforces ownership itself) and delivers it - the receiver is always the signal's own bound target, never a client-supplied value, so a private pattern can never be redirected to someone it wasn't created for. Segments travel through the existing nullable `Pattern` column as JSON (`Interaction.Segments()` decodes it) - exactly the reuse a Phase-7-era comment on that field anticipated, so Phase 11 needed no new migration on `interactions` at all. The live path's `knock.started`-style event additionally carries the real segments array in its payload (spec §20: "the pattern itself is the communication" - the receiver's device needs the actual pattern the instant it arrives to play it back locally); the push-fallback path is honestly just "you have a signal waiting," since a backgrounded app can't be handed arbitrary haptics to play through a push notification (the same limitation already flagged for Live delivery elsewhere).

**Status:** implemented - Phase 4 (Basic Pulse, live path), Phase 5 (Push Fallback), Phase 6 (Pulse Back), Phase 7 (Knock), and Phase 11 (Custom Signals). All live-validated end to end with real Keycloak users: live delivery via a real WebSocket connection (Pulse, Knock's own `knock.started`/`knock.stopped`, and now Signal's own `signal.started`/`signal.stopped`, the former carrying the real segments array); push fallback via a real presence check plus a real notification landing in Core's database, including both an honest failure (no registered device) and a genuine success once a device/push-token was registered; a full Pulse → Pulse Back round trip confirming the reciprocal direction, the `inResponseToId` link, a real single-call completion, and a 403 when a non-receiver tries to respond; a full Knock round trip for both delivery paths with durable `knock_started`/`knock_completed` analytics events; and a full Custom Signal send confirming a real WebSocket delivery of the actual composed segments, plus durable `signal_started`/`signal_completed` analytics events. Real source in `apps/pulse/api/internal/pulseinteractions/`.

Phase 5 also required a real, carefully-scoped Core change: `notifications.Service.Send` only ever allowed a caller to notify themselves or an admin to notify anyone - Pulse's sender-notifies-receiver need was the first real cross-user notification requirement this platform had ever hit. Relaxed with the user's explicit sign-off (see `backend/core-api/internal/notifications/README.md`) to allow any authenticated caller to notify any user, attributed via a new `SentByUserID` field. `realtime-gateway` also gained a small new capability: `GET /v1/presence/{userId}`, exposing its already-existing `presence.Tracker.IsOnline` as a real authenticated REST endpoint.

Mobile: `apps/pulse/mobile`'s incoming-Pulse banner now offers a real "Pulse Back" button (a separate `_IncomingPulseBanner` widget, kept private like every other screen widget in that file) wired to `PulseApi.pulseBack`. Its full receive-then-respond flow needs a real WebSocket connection to exercise end to end, which this project's test sandbox can't dial (the same honest, pre-existing gap `HomeShell`'s own realtime connection has) - covered by `flutter analyze` (clean) and the unchanged existing widget suite (no regressions), not a dedicated widget test.
