# pulse-connections

Pulse-side Friend / Close-Friend classification and permission checks layered over Core's generic relationship graph, plus Circles (product spec §10, Phase 9). The underlying connection is a Core `Relationship{Type: "pulse_friend", ...}`; "close friend" and any Pulse-specific permission flags are Pulse-owned metadata keyed by `relationship_id`, kept out of Core's product-agnostic relationship row.

**Owns:** `pulse_connection_classifications` table - the Friend/Close-Friend overlay only. The connection lifecycle itself (request/accept/decline/remove) is never duplicated; every call forwards to Core's real relationships API scoped to relationship type `pulse_friend`.
**Depends on:** Core `relationships` (connection lifecycle: request/accept/decline/remove/block), Core `groups` (Circles), `pulse-profile`.
**Circles (Phase 9):** `POST/GET /v1/pulse/circles`, `GET/POST /v1/pulse/circles/{id}/members`, `DELETE /v1/pulse/circles/{id}/members/{userId}` - a thin wrapper over Core's real `groups` capability (`backend/core-api/internal/groups`), never a Pulse-owned Circle table. Core's own `ListMine` has no `appId` filter (it returns every group the caller belongs to across every application), so `internal/pulseconnections/core/groups_adapter.go` filters to Pulse's own AppID client-side. Adding a member requires the caller and the target to already be a real, active Pulse connection (Friend or Bond) - enforced Pulse-side (`checkConnected`, mirroring pulse-interactions' own helper of the same name) *in addition to* Core's own manager-based authorization on `groups.AddMember` - a Circle can never become a way to reach a stranger. `CreateCircle` needs no separate "add myself" call: Core's real `Create` already seeds the creator as a manager member in the same transaction.
**Status:** implemented - Phase 2 (Connection Experience) and Phase 9 (Circles). Phase 2 live-validated end to end with two real Keycloak users: request → accept → asymmetric close-friend classification → duplicate-request conflict correctly forwarded from Core → remove (soft transition to `ended`, matching Core's real semantics). Phase 9 live-validated with real Keycloak users against Core's real `groups` API: creating a Circle, correct `appId` filtering on list, adding a real active connection as a member, a real 403 rejecting a non-connection, and member removal - all confirmed via real Postgres rows in both Pulse's and Core's own databases. Real source in `apps/pulse/api/internal/pulseconnections/`.
