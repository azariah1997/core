# pulse-preferences

Experience Controls (product spec §33, §34, §72, Phase 13): notification detail level (Detailed/Private/Silent) and haptic intensity are the only fields genuinely Pulse-owned - Core has no concept of either. Quiet Hours and Mute are deliberately **not** duplicated storage here, unlike this module's original planning stub assumed: both are real, already-live Core capabilities (`notifications.QuietHours`, `trustsafety.Mute`), and this module is a thin, Pulse-scoped settings surface over each - never rebuilding what Core already owns.

**Owns:** `pulse_preferences` table - `notification_detail` and `haptic_intensity`, one row per user, defaulting to today's pre-Phase-13 behavior (full detail, full intensity) so a user who never opens Settings sees no change.
**Depends on:** Core `notifications.QuietHours` (`GET/PUT /v1/notification-preferences/quiet-hours`, scoped by Pulse's own AppID, injected server-side, never client-supplied) and Core `trustsafety.Mute` (`POST/GET/DELETE /v1/trustsafety/mutes`, platform-wide, not app-scoped).
**Enforcement:** a `NotifierDecorator` (`internal/pulseprefs/pulsemodules/`) wraps the real Notifier both `pulse-interactions` and `live-touch` already use - it structurally satisfies both modules' identically-shaped `Notifier` interface (this codebase's consumer-defined-interface convention) with a single decorator type. Before any push notification is sent, it reads the **receiver's** own notification-detail preference directly from Pulse's own database (no cross-user auth boundary crossed - this is Pulse's own data, read by Pulse's own backend code, the same way `moments.Service` already freely resolves "the other participant"): `silent` skips the notification entirely (the interaction itself still succeeds and is recorded normally); `private` still sends one but with generic, content-free title/body/data; `detailed` (the default) passes the real content through unchanged. Quiet Hours needs no equivalent Pulse-side enforcement wiring at all - Core's own `notifications.Service.Send` already suppresses interruptive channels during the receiver's real quiet-hours window internally, before this phase existed.
**Named, deferred gap:** delivery-time Mute suppression (Architecture Audit's AUTHORIZATION MODEL item 7 - "does the receiver mute the sender?") is *not* wired into the Notifier decorator. Core's `trustsafety.Mute` is deliberately self-scoped (a user can only ever read their own mute list via their own token), so Pulse's sender-authenticated request has no way to ask "does the receiver mute me" without a new, unscoped Core capability (an `IsMuted(muterID, mutedID)` check, analogous to `trustsafety.IsRestricted`) - which, per this session's Phase 5 precedent for cross-cutting Core changes, needs explicit user sign-off before being added, not something to bolt on silently. The Mute CRUD surface itself (mute/list/unmute) is fully real today; only its use as a delivery gate is deferred.
**Status:** implemented - Phase 13 (Quiet Hours / Experience Controls). Live-validated end to end with the real Alice/Bob sample users against real Postgres and real Core: preferences get/set persisting and round-tripping; Quiet Hours set through Pulse confirmed to write the exact same row Core's own endpoint reads back; Mute/list/unmute confirmed against Core's real global mute table; and, most importantly, all three notification-detail states verified against a real offline-push Knock - `silent` left Bob's real Core notification count unchanged, `private` added one real notification with redacted generic content, and `detailed` (after resetting) delivered the real title/body/pattern data exactly as every prior phase already did, proving zero regression to existing behavior. Mobile ships a real Experience Controls section on the Profile tab: a notification-detail dropdown, a haptic-intensity slider (wired live into the shared `HapticEngine` instance, with an honestly-scoped coarse tier mapping since Flutter's `HapticFeedback` API has no continuous intensity control), a Quiet Hours toggle with timezone/hour-range fields, and Mute/Unmute management.
