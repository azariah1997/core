# live-touch

Flagship synchronous two-way touch feature (spec §21): session invite/accept, both participants on a real-time channel, touch-start/touch-stop routed bidirectionally with minimal latency. Session lifecycle (invite/accept/decline/end) is a durable REST flow; the touch events themselves are ephemeral realtime-only messages, exchanged directly between the two participants and never persisted or proxied through `pulse-api`.

**Owns:** `live_touch_sessions` table (lifecycle only - not individual touch events).
**Depends on:** `bond` only. Live Touch is gated on the caller's real, current active Bond partner (spec §7: Bond "unlocks... Live Touch") - a genuinely stricter authorization shape than Pulse/Knock's Friend-or-Bond, which is why this module has its own `Bond`-only check (`bond.MyActiveBond`, satisfied directly by `bond`'s real `*Service`, same "satisfied directly" pattern `mood` already established) rather than reusing `pulse-interactions`' shared `Create`/`Start`/`Stop` state machine the way Knock did. The scaffold originally also listed `pulse-connections` and `pulse-interactions` as dependencies; neither turned out to be needed - Bond gating alone is sufficient authorization (a Bond already requires a prior Friend connection to form), and "completion recorded as an interaction for Moments" is deferred to Phase 12 (Moments), which will read whatever it needs from `live_touch_sessions` directly rather than `live-touch` writing into `pulse-interactions`' own table.
**Realtime:** session lifecycle events (invited/accepted/declined/ended) are a best-effort live push via `rtbus.Publisher.ToUser`, same as every other module. Once a session is active, both participants `subscribe` to a per-session channel (`pulse:live-touch:{sessionId}`) using the mobile app's *already-open* realtime-gateway WebSocket connection (not a second connection) and `publish` touch-start/touch-stop directly to each other through the hub's real relay (`backend/realtime-gateway/internal/ws`) - live-validated end to end at **sub-millisecond** measured relay latency. `pulse-api` never sees an individual touch event.
**Delivery mode:** the *invite* (not the touch session itself) is delivered live or as a durable push, decided once via a real presence check - the same "decided once, never re-decided" discipline `pulse-interactions`' own `DeliveryMode` established.
**Timeout/disconnect:** an unaccepted invite expires after 2 minutes; an active session with no explicit `End` call expires after 30 minutes - both computed lazily on the next read (`Get`/`Accept`/`Decline`), never a background sweep job, the same pattern `mood`'s own expiry already established. This is an honest proxy for spec §104's "disconnect handled," not true instant cross-device disconnect detection: `realtime-gateway`'s hub doesn't broadcast a "peer disconnected" event to channel subscribers today - a real, documented platform limitation, not something this phase silently papers over.
**Access control on the touch channel:** the session ID itself (a cryptographically random UUID) is the only access control `realtime-gateway`'s generic channel protocol offers today - anyone who learns a session ID could `subscribe` to it. In practice a session ID is only ever revealed to its two real participants (via the REST responses and the `ToUser` lifecycle pushes), but this is a capability-based control, not a stronger per-channel ACL enforced by the hub itself - a genuine, documented platform limitation worth revisiting if Live Touch's threat model ever needs it, not a claim of stronger security than what's actually implemented.
**Latency measured (spec §104):** invite-to-accept latency is recorded as a durable analytics property (`inviteToAcceptLatencyMs`) - the one latency this phase can honestly measure server-side. Per-touch-event round-trip latency happens entirely client-to-client over the realtime channel and would need mobile-side instrumentation this phase doesn't add.
**Status:** implemented - Phase 10 (Live Touch). Live-validated end to end with real Keycloak users (the Phase 9 sample Bond pair, Alice ↔ Bob): Bond-gating correctly rejected an unbonded caller (403) and correctly resolved the real bond partner; an offline receiver got a real push notification landing in Core's database (with the real device-registration-dependent honest failure/success split already established in Phase 5); a real WebSocket round trip relayed `touch.start`/`touch.stop` directly between two dialed connections at ~790µs measured relay latency; `Accept`/`Decline`/`End` all transitioned state correctly, including a real 409 rejecting a double-accept and a real 403 rejecting a non-participant; and `End` computed a real, non-fabricated duration from `AcceptedAt` to `EndedAt` (durationless for a session that was never accepted). Mobile ships a real "Live Touch" button (shown only against the real Bond partner), an incoming-invite banner with Accept/Decline, and a `LiveTouchScreen` that reuses the app's single persistent realtime connection to publish/subscribe touch events with real local haptic feedback on both sides. Real source in `apps/pulse/api/internal/livetouch/`.
