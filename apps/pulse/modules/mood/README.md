# mood

Today's Mood: passive, wordless daily emotional broadcast. Visual selection from a predefined symbol set (never free text - spec §22-23), per-mood audience, day-boundary/timezone-correct expiry (spec §26).

**Owns:** `moods` table - a singleton row per user (Today's Mood, not a history), replaced wholesale by the next `Set`.
**Depends on:** `pulse-connections` (audience resolution against Friend/Close-Friend classification) and `bond` (`PARTNER_ONLY` audience) - both real, same-process `*Service` dependencies wired at the composition root through `internal/mood/pulsemodules`' adapters, never HTTP self-calls and never a duplicated copy of their data (mirrors this codebase's own precedent, e.g. `backend/core-api/internal/notifications`' `AdminChecker` "satisfied directly by `*authz.Service`"). Core `groups` is not yet a dependency - see Audience below.
**Audience:** five of spec §25's six values are implemented - `partner_only` (resolved from `bond`'s real active-partner record), `close_friends`/`all_connections` (resolved from `pulse-connections`' real Friend/Close-Friend classification), `custom_users` (a caller-supplied list, filtered server-side to real active connections only - never an arbitrary stranger ID), and `private` (owner only). `selected_circles` is a deliberate, documented gap: it needs Core's real `groups` capability, which Pulse has never touched, and Phase 9 (Close Friends & Circles) is explicitly the phase that integrates it - the same honest-deferral pattern as e.g. Knock's own free-form-pattern gap (Phase 11).
**Audience resolution timing:** computed once, at `Set`, from the owner's own real connections/bond state at that moment - never re-derived per viewer. This mirrors `pulse-interactions`' `DeliveryMode` ("decided once ... never re-decided mid-interaction") and solves a real access-control problem: a viewer's own request token proves who *they* are, never who the *owner* has classified as a close friend, so that resolution can only honestly happen under the owner's own credentials, at `Set` time. A later reclassification, unfriend, or bond change doesn't retroactively change who can already see a Mood that's already been set - the next `Set` recomputes it fresh.
**Expiry:** `GET` (both `/me` and by-ID) filters `WHERE expires_at > now()` server-side - an expired Mood is functionally gone for everyone, including the owner (spec §26: "do not keep stale moods indefinitely as active state"), with no background sweep job this phase (an intentionally deferred cleanup detail, matching spec §26's own "historical Mood storage is a separate product decision").
**Privacy:** viewing someone else's Mood when you're not in its audience returns the same 404 as no Mood existing at all - deliberately indistinguishable, so a caller can never probe whether an arbitrary user even has an active Mood.
**Response:** spec §27 names Pulse and Knock themselves as the non-verbal response to a Mood - both already exist (Phase 4, Phase 7) and work against any connected user ID, so this needed no new backend surface, only a mobile UI affordance pointing the existing endpoints at the Mood's owner.
**Status:** implemented - Phase 8 (Today's Mood). Live-validated end to end with real Keycloak users against real Postgres, Core's real relationships API, and real Pulse-owned classification/bond state: `partner_only` correctly resolved to a real bonded partner and excluded a plain (non-bonded) friend; `close_friends` correctly resolved against real classification data and excluded a plain friend; `custom_users` correctly dropped a supplied ID that wasn't a real active connection while keeping a real one; a real stranger and a real friend outside the chosen audience both got the same 404 as "no Mood set"; expiry landed exactly on local midnight; and Clear removed the real row. See `apps/pulse/docs/ARCHITECTURE_AUDIT.md` for the full design and real source in `apps/pulse/api/internal/mood/`.
